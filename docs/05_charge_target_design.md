# 5. 目標充電率（1%単位の充電停止）設計書

状態：実装済み（2026-09-28、ブランチ `feature/charge-target-soc`）。実装で設計から変えた点は第13章に記録した。

画面の再設計案は Design キャンバス（非公開）にある。本書の第8章はその案の文章版である。

---

## 1. 設計意図

**スーパーチャージャー無料充電の権利を持つオーナーが、自宅ではスーパーチャージャーまで走行できる分だけ充電し、残りをスーパーチャージャーで充電できるようにする。**

自宅で充電した電力には費用がかかる。買電すれば電気代を払い、太陽光の余剰を使えばその分の売電収入が減る。無料充電の権利を持つオーナーがスーパーチャージャーで充電した分には料金がかからない。したがって、自宅で充電する量を「スーパーチャージャーまで走れる量」に抑えるほど、充電にかかる費用は減る。

必要な量は、自宅からスーパーチャージャーまでの走行で消費する電力量に、余裕を加えたものである。

```text
例：片道 20km、電費 150Wh/km → 3.0kWh
    容量 75kWh の車では 3.0 / 75 = 4%
    気温・空調・渋滞による増加分として余裕を加え、目標充電率を 10% 前後に設定する
```

この用途では、目標は 10〜30% 程度になる。車両側の充電上限（`charge_limit_soc`）は50%未満に設定できない（第2.1節で実機確認済み）ため、車両側の機能だけでは止められない。そこで本システムが充電率（`battery_level`）を読み、目標に達したら `charge_stop` を送る。

目標が50%以上なら、車両側の充電上限を目標と同じ値にすれば車両自身が止まる。本システムはその値を車両に設定する。

### 1.1 設計意図から導かれる要件

以下の各要件は、上の意図から直接導かれる。後から仕様を変えるときは、この対応を崩していないか確認すること。

| # | 要件 | 意図との関係 |
| --- | --- | --- |
| R1 | 1%単位で設定できる | 必要量は走行距離で決まり、10%刻みでは過不足が大きい |
| R2 | 目標**以上**になったら止め、目標**未満**では止めない | 不足するとスーパーチャージャーまで走れない。超過（最大1%程度）は費用が少し増えるだけである |
| R3 | 外出先の充電は止めない・制限しない | スーパーチャージャーでの充電こそが意図した充電である |
| R4 | 車両側の充電上限を目標に合わせるのは、自宅の充電器に接続されている間だけ | 目標に合わせた上限（例：50%）のまま外出すると、スーパーチャージャーでもその値で止まり、無料で充電できる量が減る（R3に反する） |
| R6 | 車両側の充電上限は、車両が受け付ける範囲で目標に最も近い値にする | 車両自身が止める範囲を最大にすると、システムが停止していても目標付近で止まる |
| R5 | 目標到達後、夜間に買電で補充しない | 補充は日中の余剰電力でのみ行う（第3.4節） |

## 2. 前提（観測できる事実）

| 事実 | 根拠 |
| --- | --- |
| 車両側の充電上限は50%未満に設定できない。`set_charge_limit` に50%未満を送ると、`result: true` を返したうえで50%に切り上げる | 第2.1節の実機確認 |
| 車両データの `charge_state` は下限を `charge_limit_soc_min`（今回 50）、上限を `charge_limit_soc_max`（今回 100）として返す | 同上 |
| 日中、車両が `online` のとき、制御ループは180秒ごとに `vehicle_data?endpoints=charge_state` を読んでいる | `tesla_solar_charger.py` の日中ループ |
| その応答に `battery_level`（整数 %）と `charge_limit_soc` が含まれる | `docs/01_architecture.md` 第3章② |
| `charge_stop` 後、ケーブルが挿さったまま充電していない状態では、ウォールコネクターの `contactor_closed` は `false`、`vehicle_current_a` は `0.0` | 2026-08-22 実機確認（`wall_connector.py`）。**目標到達の `charge_stop` 直後という条件では未確認**（第11章） |
| ウォールコネクターの `vehicle_connected` は「何らかの車が繋がっている」ことを示し、制御対象の車とは限らない | `docs/03_operation.md`「既知の制約：複数の車両に対応していない」 |

### 2.1 実機確認：`set_charge_limit` に50%未満を送った場合（2026-09-28）

ラズパイ上で稼働中のプロキシとトークンを使い、一回限りのスクリプトで実行した。

| # | 操作 | 結果 |
| --- | --- | --- |
| 0 | 車両リスト | `offline` |
| — | `wake_up` | 1回目 `offline`、2回目 `online` |
| 1 | 車両データ | `charge_limit_soc: 80` / `charge_limit_soc_min: 50` / `charge_limit_soc_max: 100` / `charging_state: Complete` / `battery_level: 81` |
| 2 | `set_charge_limit` に `{"percent": 30}` | HTTP 200、`result: true`、`reason: ''` |
| 3 | 5秒後に車両データ | **`charge_limit_soc: 50`** |
| 4 | `set_charge_limit` に `{"percent": 80}`、5秒後に車両データ | `charge_limit_soc: 80`（元に戻った） |

費用は約¥6.65（ウェイク2件 ¥5.50、データ3件 ¥0.86、コマンド2件 ¥0.29）。

この結果から設計に2点を取り込む。

1. **下限は `charge_limit_soc_min` を使い、50 と決め打ちしない。**ファームウェアの更新で下限が変わっても、設計を変えずに追従できる。この値は既に読んでいる車両データに含まれ、読み取りは増えない
2. **`set_charge_limit` の成功は、`result` ではなく読み直した `charge_limit_soc` で判定する。**`result: true` は「要求を受け付けた」ことしか示さず、設定された値を示さない。`post_vehicle_command` が HTTP 200 でも本文の `result` を検証しているのと同じ考え方で、応答をそのまま成功と扱わない

## 4. 動作仕様

目標充電率が未設定（`null`）のときは、現行とまったく同じ動作をする。以下は設定されているときの動作である。

### 4.1 停止

| 条件 | 動作 |
| --- | --- |
| `Charging`、外出先でない、`battery_level >= charge_target_soc` | `charge_stop` を送る。`below_min_count` のデバウンスは待たない。成功したら `prev_charging_status = Stopped` とする |
| 上記で停止に成功 | 終端状態（`Complete` と同じ扱い）として待機する（4.6） |
| 上記で停止に失敗 | 次のサイクルで再送する |
| `Charging`、外出先（`SITE_AWAY`） | 止めない（R3）。既存の外出先の分岐がそのまま処理する |

止める主体は目標の値で分かれる。

| 目標充電率 | 車両側の充電上限（4.5） | 止める主体 | 止まった後の `charging_state` |
| --- | --- | --- | --- |
| `charge_limit_soc_min` 未満（例：30%） | `charge_limit_soc_min`（例：50%） | システムの `charge_stop` | `Stopped` |
| `charge_limit_soc_min` 以上（例：60%） | 目標と同じ（60%） | 車両自身。上表の停止判定は予備として働く | `Complete` |

停止精度（システムが止める場合）：判定は180秒周期、`battery_level` は整数である。止まる値は最大で「目標 +1% 未満 + 180秒分の充電量」になる。48A × 200V = 9.6kW なら180秒で 0.48kWh、容量75kWhで約 0.64% である。目標より下で止まることはない（R2）。車両自身が止める場合は、車両の制御に従い目標で止まる。

### 4.2 開始の抑止

| 条件 | 動作 |
| --- | --- |
| `Stopped`、`battery_level >= charge_target_soc` | 余剰電力があっても `charge_start` を送らない。4.6 と同じく待機する |
| `asleep`/`offline`、最後に読んだ `battery_level >= charge_target_soc` | `wake_up`（¥2.75/件）を送らない |

就寝中の判定はタイマーではなく、毎サイクル「最後に読んだ値」と「現在の目標」を比べて行う。目標を引き上げると、次のサイクルで起こせるようになる。就寝中の車両の充電率は増えないため、最後の値が目標以上なら、起こしても開始条件は成立しない。

### 4.3 再開

`battery_level < charge_target_soc` になったら、通常の開始判定（余剰電力が開始閾値 `START_AMPS` 以上）に戻る。余裕幅の設定値は設けない。放置による減少は1日あたり1%前後であり、補充1回で `charge_start` と `charge_stop` を1件ずつ（計 ¥0.29）送る。

### 4.4 フル充電モードとの関係

| 条件 | 動作 |
| --- | --- |
| フル充電モード中、`battery_level >= charge_target_soc` を観測 | `charge_stop` を送り、成功を確認してから `write_override(False)` で解除する |
| 上記で停止に失敗 | 解除しない。次のサイクルで停止を再送する（解除を先にすると、停止していないのにモードだけ消える） |
| フル充電モード中、`Complete` かつ `battery_level >= charge_target_soc` を観測（目標が下限以上で、車両自身が止めた場合） | `charge_stop` は送らずに解除する。この判定は終端状態の分岐（`charging_status in TERMINAL_STATUSES`）の中に置く。そこは目標の判定より前で `continue` するため、置かなければ解除されない |
| 充電率が既に目標以上のときにフル充電モードをONにした（車両 `online`） | 次のサイクルで開始せずに解除する |
| 同上（車両 `asleep`/`offline`、最後の値が目標以上） | 起こさずに解除する |

解除後、18:00〜7:00 であれば次のサイクルから夜間休止に入る。これにより、目標到達後に夜間の買電で補充することはない（R5）。

既存の「手動停止を検知したら解除」はそのまま残る。目標到達でシステムが停止したときは `prev_charging_status = Stopped` を記録するので、手動停止と取り違えない。

### 4.5 車両側の充電上限の自動設定と復元（R4・R6）

**設定すべき上限**

```text
設定すべき上限 = max(charge_target_soc, charge_limit_soc_min)
```

`charge_limit_soc_min` は、そのサイクルで読んだ車両データの値を使う。読めない（キーが無い、整数でない）ときは50とする。

| 目標充電率 | 設定すべき上限（`charge_limit_soc_min` = 50 の場合） |
| --- | --- |
| 30% | 50% |
| 50% | 50% |
| 60% | 60% |
| 100% | 100% |

**設定する条件（すべて満たすとき）**

1. 目標充電率が設定されている
2. 車両データを読んだ直後で、`charge_limit_soc != 設定すべき上限`
3. `charging_state != Disconnected`
4. 自宅の充電器に接続中

このとき、次の順で処理する。

1. 保存した上限が無ければ、いまの `charge_limit_soc` を保存した上限として `vehicle_status.json` に書く
2. `set_charge_limit`（`{"percent": 設定すべき上限}`）を送る
3. 送った値を「設定した上限」（`charge_limit_applied_soc`）として書く

**成功の判定**

`set_charge_limit` の応答の `result: true` では成功とみなさない（第2.1節：50%未満を送っても `result: true` が返り、値は切り上げられる）。次に車両データを読んだとき、`charge_limit_soc == 設定した上限` なら成功とする。一致しなければ再送し、ATTENTIONログを出す。確認のために読み取りを増やすことはせず、次のサイクルの車両データを使う。

**Teslaアプリで上限を変更された場合**

目標充電率が設定されている間に `charge_limit_soc != 設定した上限` を観測したら、利用者が変更したとみなす。変更後の値を新しい保存した上限として書き、設定すべき上限に戻す。ATTENTIONログを出す。目標充電率が設定されている間は、目標充電率を優先する。

**元に戻す条件（いずれか）**

| 条件 | 動作 |
| --- | --- |
| 自宅の充電器に未接続、かつ車両 `online`、かつ保存した上限がある | `set_charge_limit(保存した上限)` を送り、送信に成功したら保存した上限と設定した上限を消す（第13章）。車両データを読まない経路では、車両リストの `state` だけで判定する |
| 目標充電率を解除した。かつ保存した上限があり、`charge_limit_soc == 設定した上限` | 同上 |
| 目標充電率を解除した。かつ `charge_limit_soc != 設定した上限` | 利用者がTeslaアプリで変更したとみなし、送らない。保存した上限と設定した上限を消す。ATTENTIONログを出す |

目標充電率を別の値に変えた場合は、元に戻さず、新しい「設定すべき上限」を設定する（上の「設定する条件」がそのまま成立する）。

**判定できないとき**

ウォールコネクターを読み取れない（`WC_UNKNOWN`）ときは、設定も復元も行わない。判定できないまま車両の設定を書き換えない。

**スーパーチャージャーに着くまでに戻らない場合**

自宅を出てから最初のサイクル（日中は最大180秒、終端状態の待機中は最大600秒）で戻す。自宅からスーパーチャージャーまでがそれより短く、到着時に設定した上限のままでも、車両はスーパーチャージャーで充電中 `online` なので、次のサイクルで戻る。上限を引き上げると、`Complete` で止まっていた充電は車両側で再開する（実機で確認する。第11章）。

戻せないまま外出先にいる場合は、ATTENTIONログに「車両側の上限を戻せていない」ことを毎サイクル出す。利用者はTeslaアプリで上限を上げれば充電を続けられる。

### 4.6 目標到達後の待機

目標到達で停止した後、および開始を抑止した後は `TERMINAL_BACKOFF_SEC`（600秒）待機する。ただし、この待機中は60秒ごとにウォールコネクターの `contactor_closed` を読む（`home_charger_delivering()`、宅内LAN、課金なし、1回28ms）。`true` になったら待機を打ち切り、次のサイクルに入って車両データを読む。

車両が自分から充電を再開した場合（07:00 のスケジュール充電、ケーブルの挿し直し）の検知時間は、最大600秒から最大60秒に縮まる。48Aで再開した場合の超過は、1.6kWhから0.16kWhになる。

### 4.7 夜間休止中

夜間ループは現行どおり、充電を検知したら止める。追加するのは次の2点である。

- 車両データを読んだとき（`online` かつ自宅の充電器に接続中）：4.5 の「設定する条件」を判定する
- 自宅の充電器に未接続で車両データを読まない分岐：4.5 の「元に戻す条件」を判定する

## 5. 状態の保存

### 5.1 `override_state.json`（書き手：`control_server.py`、`tesla_solar_charger.py`）

| キー | 型 | 意味 |
| --- | --- | --- |
| `charge_target_soc` | 1〜100 の整数 / `null` | 目標充電率 |
| `charge_target_updated_at` | UNIX時刻 | 最後に変更された時刻 |

`override_state.py` に `read_charge_target()` / `write_charge_target()` を追加する。既存の `_write_flag` と同じく、全体を読み直してから1キーだけ書き換える。

**検査は入口で1回だけ行う**（Parse, don't validate：入口で型と範囲を確定させ、以後は再検査しない）。`control_server.py` の `POST /api/charge_target` は、`bool` を除く1〜100の `int` と `null` だけを受け付け、それ以外には HTTP 400 を返す。読む側は、ファイルを手で書き換えた場合などの不正値を「未設定」として扱い、ATTENTIONログを出す。

### 5.2 `vehicle_status.json`（書き手：`tesla_solar_charger.py` のみ）

| キー | 型 | 意味 |
| --- | --- | --- |
| `battery_level` | 整数 / `null` | 最後に読んだ充電率 |
| `charging_state` | 文字列 | 最後に読んだ充電ステータス |
| `charge_limit_soc` | 整数 / `null` | 最後に読んだ車両側の充電上限 |
| `charge_limit_soc_min` | 整数 / `null` | 最後に読んだ車両側の下限 |
| `charge_limit_applied_soc` | 整数 / `null` | 設定した上限（4.5）。Teslaアプリでの変更を見分けるために使う |
| `charge_limit_restore_soc` | 整数 / `null` | 保存した上限（4.5） |
| `target_reached_at` | UNIX時刻 / `null` | 目標到達で停止した時刻（画面表示用） |
| `observed_at` | UNIX時刻 | 車両データを読んだ時刻 |

`override_state.json` と分けるのは、書き手を1プロセスに限るためである。`override_state.json` には2プロセスが書き込み、後から書いた方の内容が残る（`override_state.py` の `_write_flag` を参照）。保存した上限が失われると車両側の上限を戻せなくなるため、この値を後勝ちの競合に巻き込まない。

書き込みは `_write_all` と同じく、一時ファイルに書いてから `os.replace` で差し替える（原子的な置き換え）。パスは環境変数 `TESLA_VEHICLE_STATUS_PATH` で差し替えられるようにする（テストで使う）。

| 目標到達・開始抑止の後の待機 | `contactor_closed` を60秒ごとに見る待機関数 `wait_watching_home_charger()`（4.6）。満充電などほかの終端状態の待機は変えない |

停止判定を外出先の判定より後に置くのは、R3 を構造で保証するためである。外出先の分岐は `continue` で抜けるため、その後に書いた停止判定は外出先の充電に到達しない。

## 8. 画面

### 8.1 構成

上から順に4つの区画を置く。現行の丸い大ボタンは廃止する。

1. **現在の充電率**：大きな数値、状態（充電中 · 6A／停止中／外出先で充電中）、帯グラフ（充電率・目標充電率・車両側の上限）、取得時刻。目標到達・外出先のときは説明文を出す
2. **目標充電率**：−／＋ボタン（1%単位）、スライダー、「{n}% に設定する」ボタン、「目標充電率を解除する」ボタン。車両側の上限をいくつに変更するか（目標と同じ値、目標が下限未満なら下限）を保存前に表示する
3. **充電モード**：太陽光追従／フル充電の2択の切替
4. **外出先の充電記録**：スイッチと費用の説明（1回あたり約¥7）

値を変えるたびには送信しない。「設定する」を押したときだけ `POST /api/charge_target` を送る。

## 12. 検討して採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| 目標の直前だけ周期を60秒に短くして超過を減らす | `vehicle_data` が1件 ¥0.287 増える。超過は最大1%程度で、R2 に反しない |
| 再開までの余裕幅（例：目標 −2%）を設定値にする | 補充は日中の余剰でのみ起き、1回 ¥0.29 である。設定値を増やす利点が小さい |
| 車両側の上限を目標に合わせたまま外出させる | スーパーチャージャーでもその値で止まり、R3・R4 に反する |
| 下限を50と決め打ちする | 第2.1節で観測した値は50だが、車両は `charge_limit_soc_min` として返している。決め打ちするとファームウェアの変更に追従できない |
| 目標をそのまま送り、拒否されたら下限へ切り替える | 第2.1節のとおり、車両は拒否せず `result: true` を返して切り上げる。拒否を検知する手段が無い |
| 目標が下限以上なら上限を変えず、システムの停止だけで止める | 車両自身が止める範囲を捨てることになり、R6 に反する。システムが停止している間は止まらない |
| 目標をkm（航続距離）で入力する | `battery_range` は車両の推定値で、気温や走り方で変わる。v1 は%で入力し、第1章の計算例で換算する |
| 画面でスライダーの値を変えるたびに送信する | 指を動かしている途中の値が保存され、制御ループがその値で判定しうる |

## 13. 実装で設計から変えた点

| 箇所 | 設計 | 実装 | 理由 |
| --- | --- | --- | --- |
| 第4.5節 元に戻す | 送った後、次に車両データを読んで一致を確かめてから記録を消す | 送信に成功した時点で記録を消す | 外出中は車両データを読まない経路（`restore_charge_limit_without_reading()`）に入る。記録を残すとその経路が同じ値を二重に送る。帰宅して接続すれば、その時点の上限を改めて保存し直すため、記録を消しても復元に必要な値は失われない |
| 第4.6節 待機 | 終端状態の待機を置き換える | 目標到達・開始抑止の後の待機だけに使う | 満充電・ケーブル未接続などの待機まで変えると、既存の挙動（ウォールコネクターへの問い合わせ回数）が変わる。設計書の本文も「目標到達で停止した後、および開始を抑止した後」と書いている |
| 第10章 テスト | T1〜T16 | `tests/test_charge_target.py`（T1〜T14 と不正値）、`tests/test_control_server.py`（T16 と状態API） | T15 は既存の `tests/test_charge_control.py` がそのまま担う。擬似車両の `set_charge_limit` は、実機と同じく下限未満を `result: true` のまま切り上げる |
