# デプロイ履歴

ラズパイへの本番デプロイを行った際の簡易記録。形式は自由、最新のものを上に追加する。

## バージョン管理の方針

軽量なSemVer（`vMAJOR.MINOR.PATCH`）のGitタグを使う。厳密な運用ルールは設けず、目安として以下の通りとする。

* 機能追加 → MINORを上げる（例: `v0.1.0` → `v0.2.0`）
* バグ修正・ドキュメント修正のみ → PATCHを上げる（例: `v0.1.0` → `v0.1.1`）
* **ラズパイへ実際にデプロイしたコミットにタグを打つ**ことで、「今ラズパイで動いているのはどのバージョンか」を `git tag` / `git describe` で確認できるようにする
* **タグを打ったら、必ず同じ内容で `gh release create` も行う。** `git tag` を push するだけではGitHubの「Releases」には反映されず（タグとReleaseは別物）、`v0.1.1`〜`v0.2.1`が一時的にタグのみでReleaseが無い状態になり、GitHub上の「Latest」表示が古いまま（`v0.1.0`）になっていたことがあった。コマンド例：
  ```bash
  gh release create vX.Y.Z --title "vX.Y.Z - 概要" --notes "英語の説明文

  ---

  日本語の説明文"
  ```
* 初回タグ：`v0.1.0`（認証情報のローテーション、`poc/`の再編成、ドキュメント整理を終えた時点のスナップショット）

## 2026-08-10〜11（外出先での充電を制御対象から外す）

**タグ：** `v0.5.0`（コミット `f272914` / PR #17）

**内容：** コマンドを送る前に「いま充電しているのは自宅か」を判定し、自宅でなければ停止・電流調整・開始のいずれも行わないようにした。

**理由：** 08-07 20:44、外出先のスーパーチャージャーでの充電を10分の間に2回停止させ、21:05に抜線されるまで、車両が再開するたびに停止させ続けた。利用者が意図した充電を妨害している。

**判別手段の選定：** `docs/03_operation.md` に記載していた対応案は2つあったが、いずれも採らなかった。

* 急速充電フィールド（`fast_charger_present` 等）だけで判定する案は、外出先のAC充電を判別できない
* `drive_state` の緯度経度を自宅座標と比較する案は、`vehicle_location` スコープの追加と再認可が必要

調査の結果、**車両側のAPIには接続先の充電器を識別する情報が一切存在しない**ことが分かった（`charge_state` の全フィールドを確認。シリアル・DIN・サイトID・位置のいずれも無い）。車両側からの判別は原理的に不可能である。

代わりに、宅内LAN上のウォールコネクター（Gen 3）のローカルAPIを読むことにした。**宅内LANから到達できること自体が「自宅の充電器である」ことの証明になる**ため、`vehicle_connected` がそのまま答えになる。位置情報案と同等の判別能力を、Tesla APIの追加リクエストもスコープ追加もなしに得られる。

| 確認日 | 内容 |
| --- | --- |
| 08-09 | 実機に到達。ファーム `26.18.0` / 品番 `1457768-02-H` / `uptime_s` 57.3日。**現行ファームでエンドポイントは生きている** |
| 08-09 | 自宅で充電中：`vehicle_connected: true` / `contactor_closed: true` / `vehicle_current_a: 21.3` |
| 08-10 | 車両不在：`vehicle_connected: false` / `evse_state: 1`（充電中は `11`）/ `prox_v: 0.0`（同 `1.5`） |

**08-10、テンフィールズファクトリーのFLASHでの充電：** 妨害は起きなかった。**フル充電モードをONにしていたためである。回避策は設計どおり機能した。**

```text
12:24:24  Disconnected                                    ← 接続前
（12:27 フル充電モード ON）
12:34:25  Charging / 21A → 目標21A → 「バランスが取れています」
12:37:27  Charging / 21A → 同上
12:40:28  Disconnected                                    ← 以降ずっと未接続
```

**停止は起こりえなかった。**理由は2つあり、どちらか一方でも成立する。

1. オーバーライド中は夜間休止そのものを迂回するため、夜間監視の停止経路に入らない
2. 日中経路でも、オーバーライド中の目標値は `max(raw_amps, MIN_AMPS)` で**常に `MIN_AMPS` 以上**になる。停止分岐の条件は `target_amps < MIN_AMPS` であり、構造上ここへ到達しない

**条件次第だったのは `set_charging_amps` の送信だけである。**当日の `charge_current_request` は 21A で `MIN_AMPS`(4) 以上だったため、目標値 `max(21, 4) = 21` が車両の現在値と一致し、送信がスキップされた。**4A未満であれば、急速充電中の車両へ電流指定を送っていた。**

なお `charge_current_request` が `null` で返る場合は `MIN_AMPS` で代替されるため（`tesla_solar_charger.py` の `raw_amps` 初期化）、目標値も 4A となって一致し、結果的に送信されない。急速充電中にこのフィールドが `null` になるかは未確認である。

**作業内容：**
- `wall_connector.py` を新設。`/api/1/vitals` と `/api/1/version` を読み、例外を外に出さず3値（接続あり／なし／判定不能）を返す
- 判定不能の場合は、既に取得済みの `charge_state` の急速充電フィールドで補い、断定できなければ従来動作に戻す。**ウォールコネクターに到達できないことが夜通しの系統充電を許す事態にはならない**
- 夜間の外出先判定では `night_stop_failures` を消費させない。長時間の外出先充電でその夜の監視が打ち切られないため
- 判定をフル充電モードより前に置いた。**外出前にフル充電モードをONにする回避策は不要になった**
- 稼働中に読めなくなった場合は状態変化時に警告を出す。自動レビューの指摘による。起動時の確認はループ前の1回きりであり、黙っていると防ごうとしている退行そのものが痕跡なく再発する
- 判定が働いたときのATTENTIONログに急速充電フィールドの実値を書き出す。FLASHでの充電時にこれらが記録されておらず検証の機会を逃したため
- 新規ユーザーが `WALL_CONNECTOR_HOST` の存在に気づけるよう、デプロイ手順書に `tesla_config.json` 専用のステップと全キーの一覧表を新設し、READMEに設定の節を追加した。未設定時の起動ログは `INFO` から `ATTENTION` へ引き上げた
- テストを61件に拡充。`wall_connector.wc_session` のみを差し替えて判定ロジック本体は実コードで駆動し、判定不能の5パターンを個別に検証する。CI設定のIPは `192.0.2.1`（RFC 5737）で、差し替え漏れがあっても実機に到達しない

**結果：** `active (running)`、md5一致（本体 `96de8786…` / 新規モジュール `9e24d957…`）。08-11 07:13 の再起動で `自宅ウォールコネクター（… / シリアル …）を確認しました。` を確認。同 07:14、自宅で充電中の状態で判定が「自宅」を返し、通常どおり太陽光追従（余剰不足のデバウンス）に入った。

**API利用料への影響：** なし。ウォールコネクターへの問い合わせはTesla Fleet APIを経由しないため、リクエスト数も請求額も変わらない。

**未検証のまま残る事項：** DC急速充電中の `fast_charger_present` / `fast_charger_type` / `charger_power` の実値。フォールバック経路（ウォールコネクターを読み取れない場合）にのみ影響し、期待どおりでなければ従来動作に落ちるためデグレは生じない。上記のログ追加により、次に外出先で充電した時点で記録される。

## 2026-08-09（起動後に余剰を測り直す／電力の生データ記録を追加）

**タグ：** `v0.4.3`（コミット `31b2990` / PR #15）

**内容：** 車両を起こした後に余剰を測り直し、その値で充電開始を判断するようにした。あわせて読み取り専用の観測ツール `tools/observe_only.py` を追加し、電力の生データをCSVに記録するようにした。

**理由：** 08-09、自宅で「不時停止」が2件発生した。

| 時刻 | 出来事 |
| --- | --- |
| 11:46:56 | 余剰1202Wを検知しWake Up（¥2.75） |
| 11:48:08 | 充電開始、6Aに設定。**判断に使ったのは11:46:56の測定値** |
| 11:51:35 | 買電1090W。デバウンス1/2、6A→4Aへ |
| 11:55:03 | 買電689W。デバウンス2/2 → 停止 |

1回のウェイクに対して7分の充電で終わった。ウェイクはこのシステムが送る中で最も単価が高い（データ取得の約10倍）。起動には最短70秒かかる（`wake_up_vehicle()` 内の60秒待機を含む）が、開始判断はその待機より前に測った値のまま行われていた。

もう1件は 12:42 の接続直後、余剰がないため 12:46 に停止させたもの。これは設計どおりの動作である。

当日の系統電力は3分ごとに±1500W程度振れていた（`2047 → 732 → 1490 → 660 → -261 → -1202 → 1090 → 689 → 401 → 843 → 613 → 1740 → 1005`）。

**作業内容：**
- 起動成功後に `get_remo_power_smoothed()` を呼び直し、その値で既存の閾値判定を行う。再測定に失敗した場合は古い値に頼らず次のサイクルへ送る。オーバーライド中は太陽光を無視する仕様のためスキップする
- **ウェイクの判断自体は変更していない。** 依然として1サンプルで発火する。別の分岐であり別の閾値設計の問題で、判断材料が無いまま動かさない
- テストを42件に拡充。「余剰が消えていれば開始しない」「再測定失敗でも開始しない」「余剰が続いていれば従来どおり開始する」の3件。最後の1件は過剰修正になっていないことを固定する
- `tools/observe_only.py` を追加。60秒間隔で瞬時電力・メーターの更新時刻・車両状態をCSVに記録する。車両へのコマンドは送らない
- `tesla_solar_charger.py` と `tools/observe_only.py` を転送し、`tesla-charger.service` を再起動（22:55）

**結果：** `active (running)`、md5一致（本体 `df19e3a…` / 観測ツール `66bd607…`）。観測ツールも稼働を確認。

**保留中の判断（A・C）：** 開始側にもデバウンスを課す案（A）と、平滑化窓を20秒から延ばす案（C）は保留とした。**判断材料が無いためである。** 制御ログが残すのは平滑化後の値をサイクル毎に1点だけで、元のサンプルは捨てられる。そのため窓長を変えた場合のシミュレーションが原理的にできず、閾値超過が30秒続いたのか2分半続いたのかも区別できない。生データ記録はこの穴を埋めるために追加した。数日ぶん貯めたうえで判断する。

**観測初日に分かったこと：** `meter_updated_at` が約60秒ごとに進んでいる。スマートメーターの更新間隔は60秒程度とみられ、これより細かくサンプリングしても新しい値は得られない可能性が高い（1日分で確定する）。

## 2026-08-06（夜間の取得失敗を即座に取り直す）

**タグ：** `v0.4.2`（コミット `6978c52` / PR #11）

**内容：** 夜間休止中のGETが通信エラーまたは5xxで失敗したとき、次の巡回を待たずその場で1回だけ取り直すようにした。

**理由：** 夜間監視は10分間隔のため、取得の1回失敗がそのまま10分の観測欠落になる。08-06 19:59、車両リスト取得が読み取りタイムアウト（10秒）し、その空白のあいだに帰宅・ケーブル接続・充電の自動開始が起きた。検知しえた唯一の巡回が失われ、次の巡回（20:09）の時点では既に利用者がアプリで停止していた。

**調査結果：**

- 直近の失敗は**全件が `GET /api/1/vehicles`（車両リスト取得）**。タイミングが根拠で、夜間は巡回開始のちょうど10秒後、日中はRemoの平滑化サンプリング（約20秒）に続く10秒後に発生している
- 失敗率は 08-05 が3.4%（約145回中5回／タイムアウト2・504が3）、08-06 が2.2%（約138回中3回）。それ以前は散発的で、06-25に2回、07-06に1回
- **ラズパイとプロキシは正常。** プロキシは稼働46日22時間・再起動0回・RSS 17MB・FD 8個。システムはロードアベレージ0.00・SoC温度42.8℃・`throttled=0x0`・`dmesg` にエラーなし。47日稼働してFD8個・RSS17MBであればソケットリークもメモリリークも否定され、「定期再起動」という対策は解消する対象が存在しないため採らなかった
- 原因は**上流（Tesla Fleet API）の応答遅延**。プロキシが返す504は「自身の上流から応答を得られなかった」ことを意味し、読み取りタイムアウトと合わせて2種類の失敗がいずれも同じ方向を指している
- 増加の一部は劣化ではなく露出。v0.4.1 が車両リスト呼び出しを約70回/日から約140回/日へ増やしており、夜間のタイムアウト2件は08-05以前には存在しなかった呼び出しで起きている。日中の3件はそれでは説明できないが、直前6週間の3件に対して3件では傾向とは言えない

**作業内容：**
- `night_proxy_get()` を新設し、夜間の車両リスト取得と `charge_state` 取得の両方を集約。通信エラーと5xxのときだけ即座に1回再試行する
- 401・408・429は再試行しない。数秒で変わる原因ではなく、かつ500未満は課金対象であるため（`docs/01_architecture.md` 第3章③）
- 日中ループは変更なし。あちらの1サイクル欠落は3分で重みが違う
- テストを39件に拡充。単発のタイムアウトと504が**同じサイクル内で**回復すること（`budget_sec` を1巡回未満に絞って担保）、再試行が即時1回までであること、401・408・429が対象外であることを固定
- `tesla_solar_charger.py` を転送し、`tesla-charger.service` を再起動（22:34）

**結果：** `active (running)`、md5一致（`cdd7cf9…`）。起動から夜間監視が正常動作し、車両 `offline` を観測して待機。

**未確認：** 再試行経路そのものは実機で踏んでいない（デプロイ時点で車両が就寝中）。失敗率2〜3%であれば数日で `すぐに再試行します` が出るため、同じサイクル内で回復しているかを後日確認する。また、上流が数分にわたって遅い場合は再試行も失敗し、従来どおり次の巡回に持ち越される。本変更は一過性の失敗に対する緩和であり、上流の遅延そのものは解消できない。

## 2026-08-05（夜間休止中の充電監視を毎サイクル化）

**タグ：** `v0.4.1`（コミット `81887d5` / PR #7）

**内容：** 夜間休止帯の充電チェックを、休止入り時の1回から10分毎の継続監視に変更。

**理由：** 「意図しない充電が継続している」との報告を受けた調査で、2026-07-31 18:07に進行中の充電を停止・確認したのち、制御側のコマンドが一切ないまま翌08-01 09:40に車両が満充電（`Complete`）で復帰していたことを確認した。v0.4.0の夜間チェックは最初に結論の出た観測で完了フラグを立て、その夜は二度と確認しない実装だったため、確認より後に始まった充電（車両側のスケジュール充電、帰宅後のケーブル接続、停止後の車両側からの再開）が最大13時間無検知だった。07-28・07-29・07-30・08-01の夜はいずれも18:00台に`offline`で、その1回の観測だけで「充電していない」と断定していた。8/1・8/2が終日`Complete`となり、日中の余剰太陽光を使えていない。

**作業内容：**
- 夜間帯は毎サイクル（10分毎）充電の有無を確認。毎回叩くのは車両リスト（`/api/1/vehicles`）のみで車両を起こさない。`asleep`/`offline`ならそこで打ち切り、充電開始時は車両が自らオンラインになるため次の巡回で捕捉する
