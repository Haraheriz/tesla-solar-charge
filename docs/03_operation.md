# 3. 運用・保守・トラブルシューティングマニュアル（日常管理の取扱説明書）

## 1. 日常の稼働監視とログの確認方法

本システムはバックグラウンドで完全自律稼働するため、通常はオペレーションを必要としない。システムの稼働状態や挙動をモニタリング・監査する場合は、以下の手順で行う。

### 1. サービスの生存確認（ヘルスチェック）

システムを構成する2つのサービスが正常に常駐しているかをワンラインで確認する。

```bash
sudo systemctl status tesla-proxy.service tesla-charger.service

```

* **正常時の状態：** 両方のサービスに緑色の文字で **`active (running)`** と表示されていること。
* **異常時の状態：** 赤文字で `failed` または `activating (auto-restart)` となっている場合は、何らかのエラーで即死ループが発生している（「3. トラブルシューティング」を参照）。

### 2. 充電制御スクリプトのリアルタイムログ確認

3分ごとに実行される太陽光余剰電力の演算、および車両への電流変更指令の履歴をリアルタイムに追跡（ストリーム表示）する。

```bash
tail -f /home/<username>/tesla-solar-charge/tesla_solar_charger.log

```

* ※ログ表示を終了するには `Ctrl + C` を押す。

#### ログ出力の解釈基準

本システムのログは以下の3つの時間帯・モードに分けて明瞭に出力される。生成AIにログをパースさせる際も、この3パターンのいずれかに分類される。

* **パターンA：昼間・充電追従稼働中（発電あり）**
```text
[2026-05-17 12:00:00] [INFO] --- 定期チェック開始 ---
[2026-05-17 12:00:01] [INFO] 車両状態: 『online』 (RemoE瞬時電力: -3500 W)
[2026-05-17 12:00:02] [INFO] 演算状況 → 目標: 16A (車両現在値: 5A / ステータス: Charging)
[2026-05-17 12:00:03] [INFO] 電流を変更調整: 5A → 16A

```


* **パターンB：昼間・車両スリープ保護中（Insomnia Defense作動）**
```text
[2026-05-17 13:15:00] [INFO] --- 定期チェック開始 ---
[2026-05-17 13:15:01] [INFO] 車両キャッシュ状態が『asleep』のため、車両を起こさず処理をスキップします。

```


* **パターンC：夜間・システム休止モード中（18:00〜翌朝07:00）**

休止帯のあいだは**毎サイクル（10分毎）**、充電が始まっていないかを確認し続ける。毎回叩くのは車両リスト（`/api/1/vehicles`）だけで、これは車両を起こさない。`asleep`／`offline` の車両は充電していないため、そこで打ち切る。

```text
[2026-05-17 18:00:00] [INFO] --- 定期チェック開始 ---
[2026-05-17 18:00:00] [INFO] 夜間休止モード中（現在時刻 18:00:00）
[2026-05-17 18:00:02] [INFO] 車両は『online』・充電状態『Stopped』のため、停止操作は不要と判断しました。
[2026-05-17 18:00:02] [INFO] 次の稼働チェックまで10分間スリープします...

```

観測結果は状況によって次のいずれかになる。

| ログ | 意味 |
| --- | --- |
| `車両は『asleep』のため充電していないと判断し、そのまま休止します。` | 就寝中の車両は充電していないため起こさない |
| `車両は『online』・充電状態『Stopped』のため、停止操作は不要と判断しました。` | 起きているが充電していない |
| `夜間休止中に充電を検知しました。『一時停止』します（N/6回目）...` → `充電の停止を確認しました。` | 充電中だったので停止させた |
| `夜間休止中の車両リスト取得に失敗しました（N/6回目）。次の巡回で再確認します。` | 通信不良。**充電なしと断定せず**10分後に再確認する |

観測結果の行は**状況が変わったときだけ**出力する。同じ状態が続く間は以下の2行のみになるため、変化した時刻がログ上で目立つ。

```text
[2026-05-17 19:30:00] [INFO] --- 定期チェック開始 ---
[2026-05-17 19:30:00] [INFO] 夜間休止モード中（現在時刻 19:30:00）
[2026-05-17 19:30:00] [INFO] 次の稼働チェックまで10分間スリープします...

```

停止を確認したあとも監視は続く。**車両側のスケジュール充電や帰宅後のケーブル接続で充電が再開しても、次のサイクル（最大10分後）で検知して再び停止させる。**


* **パターンD：フル充電モード（マニュアル・オーバーライド）継続中**
```text
[2026-05-17 21:00:00] [INFO] --- 定期チェック開始 ---
[2026-05-17 21:00:00] [ATTENTION] フル充電モード継続中（ON から3時間12分経過／夜間休止を迂回中）：太陽光の発電状況に関わらず最大48Aで充電します。
[2026-05-17 21:00:01] [INFO] 車両状態: 『online』 (RemoE平均電力: オーバーライド中（太陽光は無視）)

```


#### ログレベル `ATTENTION` について

本システムは標準の `INFO` と `WARNING` の間に独自の **`ATTENTION`（値25）** を定義している。

フル充電モードは利用者が意図して入れる正常な状態であり `WARNING` では意味が強すぎる。一方で `INFO` に埋もれると切り忘れに気づけない。そのため「**異常ではないが人間の注意を向けたい事実**」を専用レベルとして分離している。ログを監視・パースする際は、`ATTENTION` 行を「エラーではないが確認すべき事象」として扱うこと。現在このレベルが使われるのは以下の4種類である。

* フル充電モードの継続通知（ON からの経過時間つき、毎サイクル）
* 手動での充電停止を検知してフル充電モードを自動解除したとき
* 外出先での充電と判断してコマンドの送信を見送ったとき（毎サイクル）
* 起動時、自宅ウォールコネクターのシリアルが設定と一致せず、外出先判定を無効化したとき


### 3. API利用料の確認

Tesla Fleet APIは従量課金である（単価とカテゴリ別の内訳は `docs/01_architecture.md` 第3章③を参照）。実際の使用量と請求額は、Tesla開発者ダッシュボードの **「請求と使用状況」**（`developer.tesla.com/dashboard/usage`）で、カテゴリ別のリクエスト数とともに確認できる。請求サイクルは毎月1日開始。

実績は約¥15/日（約¥450/月）で、月額割引 ¥1,448 の範囲に収まっている。制御ロジックを変更してAPI呼び出しの頻度や種類を増やすときは、このページで想定どおりの増加に留まっているかを確認すること。特に **ウェイクは単価がデータの約10倍**（¥2.75/件）で、しかもリトライ1回ごとに課金されるため、Wake Upを誘発する変更はリクエスト数以上に費用へ響く。

## 2. 夜間・任意タイミングでの動作確認（`--force-run`）

充電制御ロジック（余剰検知 → 車両起動 → 充電開始/停止 → 電流調整）は、太陽光が発電していない夜間や、Nature Remoの実測値が0の状態では検証できない。これを回避するため、`tesla_solar_charger.py` には動作確認専用のモードが用意されている。

```bash
python tesla_solar_charger.py --force-run
```

（`FORCE_RUN=1` 環境変数でも同様に有効化できる。）

* **夜間休止モード（7:00-18:00以外は停止）を無視**して常時稼働する。
* 各サイクルごとに、画面で仮想の家庭消費電力（W）を入力できる（**負の値＝売電中・余剰あり**、**正の値＝買電中**）。空Enterなら実測値を使う。

```text
[FORCE_RUNモード] 仮想の家庭消費電力(W)を入力（負の値＝売電中/余剰あり、空Enterで実測値を使用）: -3000
```

* これにより、深夜でも余剰電力を自由に変化させながら、車両の起動・充電開始・電流調整・充電停止までの一連の挙動を実機で確認できる。
* **動作確認専用のモードであり、本番運用（`tesla-charger.service`）では使用しない。** ラズパイのsystemdサービスは常に通常モード（`--force-run` なし）で起動する。

## 2.5 読み取り専用の観測ツール（`tools/observe_only.py`）

制御ログは平滑化後の値を1サイクルにつき1点しか残さない。窓長や閾値を変えたときの影響を後から検証できないため、電力の生データを別途記録する手段として用意してある。**車両へコマンドは一切送らない。**

* 60秒間隔で系統電力・メーター更新時刻・車両状態を `observe_power.csv` へ追記する
* 600秒間隔で車両状態を問い合わせる（`online` のときだけ `vehicle_data` を叩く）

### 常用しない

**Tesla API の課金が発生する。**制御ループとは独立して車両を問い合わせるためである。

| | 実績 |
| --- | --- |
| 稼働期間 | 2026-08-09 22:55 〜 08-18（8.92日） |
| `vehicle_data` の推定回数 | 約660回 |
| 費用 | **約¥190（¥21/日）** |

同期間の制御ループ自体の実績は約¥15/日であり、**観測ツールを動かすと費用が倍以上になる。**必要な期間だけ動かし、目的を果たしたら止めること。

### 起動と停止

```bash
sudo systemctl start tesla-observer.service     # 開始
systemctl is-active tesla-observer.service      # 状態確認
sudo systemctl stop tesla-observer.service      # 停止
```

**`enable` してはいけない。**再起動のたびに自動で動き出し、費用が継続する。既定では `disabled` にしてある。

```bash
systemctl is-enabled tesla-observer.service     # disabled であること
```

記録先は `observe_power.csv`（追記）と `observe_only.log`。CSVは停止しても消えないため、再開すれば続きから追記される。

### 過去の稼働で分かったこと

2026-08-09〜18 の12,700サンプルから、以下が確定した。

* **スマートメーターの更新間隔は中央値61秒**（60秒が95%）。制御ループの平滑化窓は `REMO_SAMPLES(3) × REMO_SAMPLE_INTERVAL_SEC(10)` ＝ 20秒しかなく、**大半は同一の値を3回平均している。**窓を広げる案は、複数の更新をまたぐのに120〜180秒を要し、制御サイクル（180秒）の全部を消費するため採れない
* **余剰が開始閾値を超えた81区間のうち58%が2分以内に終息していた。**3分サイクルで模擬すると、開始条件を満たす86サイクルのうち2サイクル連続を要求すれば39回（45%）まで減る

**この2点はいずれも実装に反映済みである。**`REMO_SAMPLES` を 1 にし、就寝中の車を起こす判断に `WAKE_DEBOUNCE_CYCLES`（既定2）を導入した。

## 3. スマホからの「フル充電モード」切替（マニュアル・オーバーライド）

太陽光の発電状況に関わらず充電したい場合（来客時の急ぎ充電、出発前の追加充電など）に使う機能。`tesla-override.service` が宅内LAN上で軽量Webサーバーとして常駐しており、スマートフォンのブラウザからトークン付きURLにアクセスするだけでON/OFFを切替えられる。

### 使い方

1. **初回のみ：URLをブックマーク／ホーム画面に追加**
ラズパイのIPアドレスと、`tesla_config.json` に設定した `CONTROL_TOKEN` を使って以下の形式のURLを開く。

```text
http://<ラズパイのIPアドレス>:8090/?token=<CONTROL_TOKEN>

```

トークン入りURLを毎回手で組み立てる代わりに、同梱の `show_control_url.sh` を使うと、URLと端末上のQRコードを一度に表示できる。

```bash
ssh <ホスト名> "./tesla-solar-charge/show_control_url.sh"

```

`tesla_config.json` の `CONTROL_TOKEN` と、Tailscaleの自ホストMagicDNS名（`tailscale status --self` から取得）からURLを組み立て、`qrencode`（事前に `sudo apt-get install qrencode` が必要）でQRコードを端末に描画する。Tailscale未導入の環境では動作しないため、その場合は上記のIPアドレス形式のURLを直接使うこと。スマホでQRコードを読み取れば、トークンを手で入力せずそのままアクセスできる。

URLが分かれば、iPhoneのSafariなら共有メニューから「ホーム画面に追加」、AndroidのChromeなら「ホーム画面に追加」を選ぶと、アイコンタップだけでアプリのように開けるようになる（PWA対応により、専用アイコン付きでスタンドアロン表示される）。

> **iOS/Android差異の注意：** iOS Safariは平文HTTPでも「ホーム画面に追加」が機能する。一方、AndroidのChromeは正式なPWAインストール（Service Worker登録・スタンドアロン起動）にHTTPSまたは`localhost`を要求するため、宅内LANの平文HTTP（`http://<ラズパイのIP>:8090/...`）ではホーム画面への追加自体は可能でも、完全なPWA体験にはならない場合がある。Androidでも完全なPWA体験が必要な場合は、Tailscale等のVPN経由でTLS証明書付きのホスト名からアクセスする構成を推奨する。

2. **トグルボタンをタップ：**
画面中央の丸いボタンをタップすると「フル充電モード：ON」に切替わり、太陽光の余剰計算を無視して `MAX_AMPS` でのフル充電が始まる（車両が就寝中の場合は自動で起動する）。もう一度タップすると通常の太陽光追従モードに復帰する。

3. **状態確認：**
ページは5秒ごとに自動で状態を再取得するため、他の場所（PC等）から切替えた場合でも画面を開けば最新状態が反映される。

### 注意点

* 宅外からアクセスする場合は、ルーターのポート開放ではなく **Tailscale等のVPN経由でのアクセスを推奨する**（`CONTROL_TOKEN` をURLに含めて宅外公開すると、漏洩時に第三者から充電を操作されるリスクがあるため）。
* `CONTROL_TOKEN` は `openssl rand -hex 32` 等で生成した推測不可能な値を `tesla_config.json` に設定すること。

### 就寝中の車を起こす判断（`WAKE_DEBOUNCE_CYCLES`）

**余剰が開始閾値以上のサイクルが2回連続するまで、就寝中の車両を起こさない。**

```text
[INFO] 開始閾値以上の余剰を検知しました（1/2回目）。一過性の可能性があるため、次のサイクルでも続いていれば車両を起動します。
```

開始閾値の超過は**58%が2分以内に終息する**（2026-08-09〜18 の観測で81区間中47件）。1サンプルで起こすと、消えた余剰のためにウェイク（¥2.75。このシステムが送る中で最も単価が高い）を費やすことになる。2026-08-13 12:42、余剰2236Wで起動したが12:47には1198Wへ落ちており、充電を開始できないままウェイクだけが無駄になった。

**既に `online` の車の充電開始は遅らせない。**そちらの誤発火は約¥0.3であり、3分の遅れと引き合わない。デバウンスがかかるのは「就寝中の車を起こすかどうか」だけである。

**フル充電モード中は待たない。**利用者が意図して起こしているため、余剰の継続を要求する理由がない。

なお、起動後にはさらに余剰を測り直してから開始を判断する（v0.4.3 で追加）。起動に70秒以上かかるあいだに余剰が変わるためで、こちらは別の防御線である。

### フル充電モードの自動解除と時間経過の可視化

* **時間経過による自動解除は行わない。** フル充電モードは利用者が意図して入れる状態であり、システムが勝手に打ち切ると「朝までに充電しておきたい」といった用途を壊すため。ONにしたまま放置すれば、太陽光発電量にも夜間休止（18:00〜翌07:00）にも関わらず充電が継続する。
* 代わりに、ONの間は**毎サイクル `[ATTENTION]` ログに ON からの経過時間が出力される**。切り忘れの有無はここで確認できる。
```bash
grep ATTENTION /home/<username>/tesla-solar-charge/tesla_solar_charger.log | tail -5
```
* **Teslaアプリや車内から充電を停止すると、フル充電モードは自動的に解除される。** システムが `charge_stop` を送っていないのに「充電中 → 停止」の遷移を観測した場合、それを利用者の明確な意思表示とみなし、フル充電モードをOFFにして太陽光追従モードへ復帰する。このときPWAの表示も（5秒以内に）自動で「太陽光追従モード」に戻る。
```text
[ATTENTION] 手動での充電停止を検知したため、フル充電モードを自動解除しました。太陽光追従モードに復帰します。
```

> **注意：** 上記の自動解除が働くのはフル充電モードON中の手動停止に対してのみである。**太陽光追従モード（通常稼働）で日中に手動停止した場合、余剰電力が開始閾値を超えていれば最大3分後に充電が再開される。** これは余剰電力を自動追従するという本システムの設計どおりの挙動であり、日中に確実に充電を止めたい場合は充電ケーブルを抜くこと。

### `CONTROL_TOKEN` 漏洩時のローテーション手順

URLを誤って共有してしまった、画面のスクリーンショットに含めてしまった等で `CONTROL_TOKEN` が漏洩した（あるいは漏洩した疑いがある）場合は、以下の手順で速やかに無効化する。

1. **新しいトークンを生成：**
```bash
openssl rand -hex 32
```

2. **ラズパイ側の設定を更新：**
`/home/<username>/tesla-solar-charge/tesla_config.json` の `CONTROL_TOKEN` を新しい値に書き換える。古いトークンを使ったリクエストはこの時点から即座に `403 Forbidden` になる。

3. **コントロールサーバーを再起動：**
```bash
sudo systemctl restart tesla-override.service
```
（`control_server.py` はプロセス起動時に `tesla_config.json` を読み込む実装のため、ファイル更新だけでは反映されない。）

4. **スマホ側の再設定：**
古いトークン入りのブックマーク・ホーム画面アイコンは無効になるため削除し、`show_control_url.sh` で新しいURL・QRコードを表示してホーム画面に追加し直す。

## 4. トークン失効・更新時の「初回手動認証方式」復旧手順

テスラのAPI認可トークン（`tesla_tokens.json`）が完全に失効した場合、あるいは初回認証を行う場合、Linux（ヘッドレス環境）からではブラウザセキュリティ（Private Network Access: PNA制限）により直接の認証着地がブロックされる。

これを完全に迂回するため、以下の「Windows側でトークンを取得し、Linuxへ転送する」手順を厳格に執行する。

### トークン更新の3ステップフロー

```text
【手元のWindows PC】                     【Linuxサーバー】
 1. スクリプトを一時的に直接実行
    (ブラウザが開き認証成功)
 2. tesla_tokens.json が生成 →→(SCP転送)→→ 3. 指定ディレクトリへ上書き配置
                                           4. サービス再起動で完全復旧

```

### 具体的実行コマンド

1. **手元のWindows側での作業：**
Windows側の作業フォルダ（Python環境がある場所）で、一時的にメインスクリプトを直接実行する。
```powershell
python tesla_solar_charger.py

```


自動的にブラウザが立ち上がり、テスラの公式ログイン画面が表示される。ログイン完了後、画面が白くなりWindowsのコンソール側に `[INFO] トークンを新規保存しました。` と表示されれば成功。フォルダ内に最新の `tesla_tokens.json` が生成される。
2. **Linux側への転送：**
生成された `tesla_tokens.json` を、Linux側の対象ディレクトリへ上書き転送（SCP等）する。
* 転送先：`/home/<username>/tesla-solar-charge/tesla_tokens.json`


3. **権限修復とサービス再起動：**
Linuxのコンソールに入り、以下のコマンドでトークンファイルのパーミッションを厳格化し、システムを再バインドする。
```bash
# 所有者のみ読み書き可能に制限（セキュリティ担保）
chmod 600 /home/<username>/tesla-solar-charge/tesla_tokens.json

# サービスをリスタートして新しいトークンを読み込ませる
```

## 5. 緊急時のトラブルシューティング（障害対応）

### 事象1：プロキシが `status=1/FAILURE` で即死を繰り返す

* **想定原因A：** 過去に手動テストした際のプロキシプロセスがゾンビ化して裏で生き残っており、ポート `4443` を既に占有している。
* **対応策A：** 以下のコマンドで幽霊プロセスを強制パージ（殺害）した後に再起動する。
```bash
# 4443番ポートを掴んでいるプロセスID(PID)を特定してキル
sudo fuser -k 4443/tcp

# サービスを再起動
sudo systemctl restart tesla-proxy.service

```


* **想定原因B：** Windowsから鍵ファイルを転送した際、改行コードが Windows形式（`CRLF`）になっており、Linuxの暗号ライブラリがパースに失敗している。
* **対応策B：** 改行コードをLinux標準の `LF` に一発置換する。
```bash
sudo apt-get install dos2unix -y  # 未導入の場合のみ
dos2unix /home/<username>/tesla-solar-charge/*.pem
sudo systemctl restart tesla-proxy.service

```



### 事象0：充電が制御されていない気がする（サービスは `running` なのに何も起きない）

サービスが生きていてもトークンが失効していると、車両へ一切コマンドを送れないまま無言でループし続ける。**この状態は `systemctl status` では緑色の `active (running)` に見える**ため、必ずログのレベルで確認する。

```bash
grep -E "CRITICAL|ATTENTION" /home/<username>/tesla-solar-charge/tesla_solar_charger.log | tail -20
```

* `リフレッシュトークンが失効しています（HTTP 401）` → 「4. トークン失効・更新時の『初回手動認証方式』復旧手順」を実行する。
* `トークンのリフレッシュがN回連続で失敗しています` → 同上。ネットワーク障害が疑われる場合は先に外部疎通を確認する。

リフレッシュ失敗が続く間、再試行間隔は 180秒 から最大 3600秒 まで自動的に伸びる（Tesla認証サーバーへの無駄な連打を避けるため）。復旧後は最初の成功で間隔がリセットされる。

トークンが正常な場合、次のログが続いているなら**故障ではなく仕様どおりの待機**である。

```text
[INFO] 満充電に到達済みのため、充電コマンドの送信をスキップします。10分待機します。
[INFO] 直近の充電状態（Complete）から充電不要と判断し、車両を起こさずに待機します。
```

`battery_level` が `charge_limit_soc` に達すると充電ステータスは `Complete` になり、余剰電力があってもコマンドを送らない（満充電の車へ `charge_start` を送り続けても状態は変わらず、車両を無駄に起こしAPIを浪費するだけのため）。**その日の余剰太陽光を充電に使いたい場合は、Teslaアプリで充電上限を引き上げる。**上限に達したままだと、晴天でも終日この待機ログが続く。

### 事象1.5：夜間なのに充電が止まっていない

夜間休止帯（18:00〜翌07:00）は10分毎に充電の有無を確認し、充電中であれば `charge_stop` を送って止める。停止も状態確認も、**確認できるまで10分間隔で再試行**する。連続6回確認できなかった場合はその夜の再試行を打ち切り（レートリミット429の誘発を避けるため）、次のログを出す。

```text
[CRITICAL] 夜間休止中の充電状態を6回連続で確認できませんでした。系統からの充電が継続している可能性があります。手動で確認してください。
```

**先に「外出先での充電を制御しない」を確認すること。**車両が自宅のウォールコネクターに接続されていないと判定された場合、システムは意図的に停止させない。この場合は `ATTENTION` 行が出ており、上記の `CRITICAL` には至らない。

```bash
grep ATTENTION /home/<username>/tesla-solar-charge/tesla_solar_charger.log | tail -5
```

この行が出ていたら、Teslaアプリで実際の充電状態を確認し、必要なら手動で停止すること。原因は多くの場合プロキシ（4443番）または車両との通信不良なので、あわせて「事象1」「事象2」を確認する。カウンタは確認できた時点で0に戻るため、通信が正常な夜はこの行に到達しない。

夜間の取得が通信エラーまたは5xxで失敗した場合は、**次の巡回を待たずその場で1回だけ取り直す**。

```text
[WARNING] 夜間休止中の取得に失敗しました（1/2回目）: ... Read timed out. (read timeout=10)。すぐに再試行します。
```

巡回間隔が10分あるため、1回の失敗をそのまま次の巡回まで持ち越すと10分の観測欠落になる。2026-08-06 19:59 に車両リスト取得が読み取りタイムアウトし、その10分のあいだに帰宅・ケーブル接続・充電開始が起きて検知できなかった。この行が頻出する場合は上流（Tesla Fleet API）の応答遅延であり、ラズパイ側の問題ではないことが多い。401・408・429は原因が別であり再試行しない。

#### 車両側スケジュール充電の運用方針（意図的に設定する）

Teslaの既定動作では、**充電上限未満の状態でケーブルを接続すると即座に充電が始まる。**このシステムは開始を防げず、事後に停止させることしかできない。夜間休止帯であれば10分以内に停止するが、帰宅のたびに数分間の系統充電が発生する（2026-08-06 20時頃、実際にこれが起きた）。

これを抑止するため、**車両側のスケジュール充電を意図的に設定する。**スケジュール充電が有効なとき、車両は接続しても指定時刻まで充電を開始しない。

この抑止効果は 2026-08-08〜09、`tesla-charger.service` を停止した状態で確認した。16:47（枠外）に接続しても充電は始まらず `scheduled_charging_pending = True` で待機し、夜通し変化せず、翌 07:09 に予定どおり開始した。

**時間帯は必ず日中（07:00〜18:00）の内側に置くこと。**夜間帯に置くと、設定時刻に車両が充電を開始し、システムが10分以内に停止させる、という綱引きが毎晩発生する。日中であれば、余剰があれば電流追従に乗り、なければデバウンス後に停止する通常の制御で処理される。

現在の設定は **07:00 開始 / 15:00 終了**。副作用として次の2点を織り込んでいる。

* 07:00 台はまだ買電側のことが多く、開始直後に余剰不足と判定されてデバウンス後に停止する。実測は 08-07 が約21分、08-08 が約11分だった。**デバウンス2サイクル（約6分）で収まるとは限らない。**巡回が408や取得失敗で飛ぶと、その分だけ停止が遅れる（08-07 は 07:07 の巡回が408で10分待機に入ったため長引いた）
* 15:00 以降に余剰が出た場合、システムは充電開始を試みる。車両が時間枠外の開始を拒否する場合、`充電の開始を確認できませんでした` が繰り返される可能性がある（未確認）

#### 車両側の充電開始トリガーを確認する

`charge_state` に次のフィールドがある。

| フィールド | 意味 |
| --- | --- |
| `scheduled_charging_mode` | `Off` / `StartAt`（開始時刻指定）/ `DepartBy`（出発時刻指定） |
| `scheduled_charging_pending` | 予約充電が待機中か |
| `off_peak_charging_enabled` | オフピーク充電の有効・無効 |
| `preconditioning_enabled` | 出発時刻に合わせたプレコンディショニング |

**`scheduled_charging_mode` でスケジュール設定の有無は判定できない。**このフィールドが表すのは「いま接続しているセッションにスケジュール充電の予定があるか」であって、車両にスケジュールが設定されているかではない。2026-08-08 の観測で、同一車両・同一設定のまま次のように変化した。

```text
16:37 充電状態=Disconnected  scheduled_mode=Off     pending=False   ← ケーブル未接続
16:47 充電状態=Stopped       scheduled_mode=StartAt pending=True    ← 接続、枠外なので待機
07:09 充電状態=Charging      scheduled_mode=StartAt pending=False   ← 枠に入り開始
```

**ケーブル未接続のときは常に `Off` を返す。**この状態で読んで「スケジュールは設定されていない」と判断してはいけない。満充電（`Complete`）で予定が消化済みのときも `Off` になる。

設定そのものを確認するなら、**Teslaアプリの「予約を設定する」画面を見るのが確実**である。APIで判定したい場合は、ケーブルが接続され、かつ未充電（`Stopped`）のタイミングで読むこと。

`scheduled_departure_time` には設定を解除しても過去の値が残ることがあるため、時刻の値だけを見て判断しないこと。

確認は車両が `online` のときに限る。**この確認のために `wake_up` を送ってはいけない。**設計思想（Insomnia Defense）に反するうえ、ウェイクは単価が最も高い（`docs/01_architecture.md` 第3章③）。乗車時や充電開始時など、車両が自らオンラインになるタイミングを使う。

**読み取った値は「読み取った時点」の状態でしかない。**設定は利用者がいつでも変更できるため、事後に読み取った値を過去の事象の根拠にしてはいけない。2026-08-05、4日前（07-31）の事象について当日の読み取り値を根拠に原因を判定しかけた。結論自体は利用者への確認と一致したが、根拠としては成立していなかった（しかも上記のとおり、その読み取り値自体が設定の有無を示すものではなかった）。過去の事象を判定する際は、その時点の設定を知る手段（利用者への確認）を用いること。

### 事象2：Python側が `status=1/FAILURE` で即死する

* **想定原因：** 大前提であるGoプロキシ（4443番ポート）が何らかの理由で落ちているため、Python側が通信を拒否され（Connection Refused）自死している。
* **対応策：** まず `sudo journalctl -u tesla-proxy.service -n 20 --no-pager` を叩き、プロキシが死んでいる根本原因（鍵の不整合など、仕様書第5章を参照）を排除してプロキシ側を先に緑色の `running` に戻すこと。

### 事象2.5：車両がコマンドを拒否する（`car could not execute command`）

プロキシも通信も正常だが、車両側がコマンドの実行を断っている状態。**本システムの不具合ではない。**ログには理由が付く。

```text
[WARNING] 充電停止コマンドに失敗しました（1/3回目）: car could not execute command: High energy features disabled during soh test
```

`High energy features disabled during soh test` は、車両がバッテリーのSoH（State of Health）テストを実行中で、Tesla側が遠隔からのエネルギー系コマンドを無効化していることを示す。**充電の停止も電流の変更も受け付けない。**

2026-08-14 19:42〜20:33、夜間休止帯にこれが発生し、`charge_stop` が18回（6サイクル × 3リトライ）すべて拒否された。システムは設計どおり6回まで再試行したうえで打ち切り、CRITICAL で報告している。

```text
[CRITICAL] 夜間休止中の充電状態を6回連続で確認できませんでした。系統からの充電が継続している可能性があります。手動で確認してください。
```

**対応：** システム側で取れる手段はない。SoHテストが完了するまで待つか、充電を止める必要があれば充電ケーブルを抜く。テストは満充電まで充電を継続する必要があるため、その夜は系統からの充電が続く。

### 事象3：自宅ウォールコネクターに到達できない

外出先判定に使うローカルAPIが読めない状態。**制御そのものは止まらない**（判定不能として従来動作へ縮退する）が、外出先での充電を妨害しうる状態に戻っているため復旧させる。

起動時から読めない場合と、稼働中に読めなくなった場合で行が異なる。

```text
[WARNING] 自宅ウォールコネクター（<ウォールコネクターのIP>）を読み取れませんでした。各サイクルで再試行します。
[WARNING] 自宅ウォールコネクター（<ウォールコネクターのIP>）を読み取れなくなりました。外出先かどうかを判定できないため、急速充電フィールドで補います。断定できない場合は従来どおり停止・電流制御を行います。
```

後者は**状態が変わったときだけ**出力する（3分毎に同じ行を並べないため）。読めるようになったときも1行残るので、`grep` で復旧の有無を確認できる。

```text
[INFO] 自宅ウォールコネクターの読み取りが回復しました。
```

この警告が出たまま回復していない間は、**外出先での充電を止めてしまう従来の挙動に戻っている**（急速充電フィールドで断定できる場合を除く）。放置しないこと。

まず、ラズパイから直接叩いて切り分ける。

```bash
ssh <ホスト名> "curl -s --max-time 5 http://<ウォールコネクターのIP>/api/1/vitals"
```

* **JSONが返る：** ラズパイからは到達できている。`tesla_config.json` の `WALL_CONNECTOR_HOST` の値を確認する
* **何も返らない、またはタイムアウトする：** 以下の順に確認する
1. ウォールコネクターのWi-Fiが宅内LANに接続されているか（Teslaアプリの充電器設定画面）
2. IPアドレスが変わっていないか。ルーターのDHCPクライアント一覧で実アドレスを確認する。**再発を防ぐため、ルーター側でDHCP予約を設定すること**
3. 上記が正常なら、ウォールコネクター側の一時的な不調が疑われる。長時間の連続ポーリングでローカルAPIが応答しなくなり、ブレーカーでの電源再投入でのみ復旧した事例が報告されている（evcc の Issue #28525）。本システムの問い合わせ間隔は昼3分・夜10分であり、報告されている30〜60秒間隔より1桁ゆるい

起動時に `ATTENTION` でシリアル不一致が出ている場合は、設定した `WALL_CONNECTOR_SERIAL` と応答が食い違っている。設定したIPアドレスが別の機器を指しているため、**この場合は外出先判定そのものが無効化されている**。

```text
[ATTENTION] 自宅ウォールコネクターのシリアルが設定と一致しません（設定: ... / 応答: ...）。外出先の充電判定を無効化します。IPアドレスの設定を確認してください。
```

### 外出先での充電を制御しない

**このシステムはコマンドを送る前に「いま充電しているのは自宅か」を判定し、自宅でなければ何も送らない。**対象は停止・電流変更・開始のすべてである。

2026-08-07 20:44、外出先のスーパーチャージャーでの充電を、10分の間に2回停止させた。車両が再開するたびに停止させており、21:05 に抜線されるまで続いた。この対策として導入した。

```text
[2026-08-07 20:44:57] 夜間休止中に充電を検知しました。『一時停止』します（1/6回目）...
[2026-08-07 20:44:58] 充電の停止を確認しました。
[2026-08-07 20:54:59] 夜間休止中に充電を検知しました。『一時停止』します（1/6回目）...
[2026-08-07 20:54:59] 充電の停止を確認しました。
```

#### 判定の方法

**このシステムは「外出先だと断定できたか」だけを判定する。「自宅である」とは断定しない。**自宅の充電器に何かが繋がっていることは分かっても、それが制御対象の車である保証がないためである（「既知の制約：複数の車両に対応していない」を参照）。

| 判定 | 挙動 |
| --- | --- |
| 外出先と断定できた | **コマンドを一切送らない** |
| 断定できない | 従来どおり制御する |

断定の根拠は2つあり、**車両側から先に評価する。**

##### 根拠1：DC急速充電を検知した（車両側）

**自宅の充電設備はACである。したがってDC充電なら自宅ではありえない。**場所を直接判定しているのではなく、設備の性質から自宅を排除している。この論法が成立するのはDCのときだけで、ACでは何も言えない。

判定には、既に取得済みの `charge_state` を使う。**追加のAPI呼び出しは発生しない。**

1. `fast_charger_present` が `true`
2. `charger_power` が `FAST_CHARGER_POWER_KW`（既定15kW）を超える

**閾値の根拠は設定値である。**自宅の上限は `MAX_AMPS`(48A) × 200V ＝ 9.6kW であり、これを超える給電は自宅の設備では起こりえない。**`MAX_AMPS` を変更したら `FAST_CHARGER_POWER_KW` も見直すこと。**

これは車両ごとの情報であるため、**別の車が自宅の充電器を使っていても影響を受けない。**この順序で評価するのはそのためである。

**`fast_charger_type` は判定に使わない。**自宅のAC充電で `'ACSingleWireCAN'` を返すため、「空でも `<invalid>` でもなければ外出先」という否定形の判定は自宅の充電に必ず一致する。2026-08-13・14・18 に、自宅で充電中の車を3回「外出先」と誤判定した（うち08-18 07:12 は48A・10,671W買電中で、絞り込みが3分23秒遅れ約0.50kWhを余計に買電した）。

肯定形（既知のDC種別のみ一致）にする案も採らない。観測できたDC側の値は `'Tesla'` の1件だけであり、それは同じ場面で `fast_charger_present=True` が立っていて判定材料として何も足さない。未観測の値を並べれば、誤って外出先と判定する側へ倒れる。**条件を足す誤りと落とす誤りではリスクが非対称で、余計な値があると自宅の充電を制御しなくなる**（夜間なら停止漏れ）のに対し、足りなくても他の条件へ落ちるだけである。

##### 根拠2：自宅の充電器に何も繋がっていない（ウォールコネクター）

```text
GET http://<WALL_CONNECTOR_HOST>/api/1/vitals → vehicle_connected
```

`false` なら、いま充電中の車は自宅にいない。**これは所有台数に関係なく成立する。**Tesla APIの呼び出しは1件も増えず、課金も増えない。

**`true` は根拠にしない。**「何らかの車が繋がっている」ことしか意味せず、それが制御対象の車である保証がない。`/api/1/vitals` にVINは含まれない。

読み取りに失敗した場合は、その場で1回だけ取り直す（`WALL_CONNECTOR_ATTEMPTS`、既定2）。それでも読めなければ根拠2は使えず、根拠1だけで判断する。次の5つは区別せず「読めなかった」として扱う。

1. TCP接続が確立できない（ウォールコネクターの電源断、Wi-Fi切断、IPアドレスの変更、LAN障害）
2. 応答がタイムアウトする（既定5秒）
3. HTTPステータスが200以外
4. レスポンスがJSONとして解釈できない
5. JSONに `vehicle_connected` キーが無い、または真偽値でない

##### どちらの根拠も得られない場合

**判定を諦め、従来どおりの動作に戻る**（夜間なら停止させる）。ここで停止を見送ると、自宅での夜通しの系統充電を許すことになるためである。

#### 観測記録

以下は**個々の観測であり、値の範囲や仕様を示すものではない。**同じ状況で同じ値が返る保証はなく、判定ロジックをこれらの値に合わせて調整してはいけない。判定が働くたびに `ATTENTION` ログへ実値を書き出しているので、観測が増えたら追記したうえで再検討すること。

| 日時 | 状況 | 観測値 |
| --- | --- | --- |
| 2026-08-18 18:52 | スーパーチャージャーで充電中（夜間休止帯） | `fast_charger_present=True` `fast_charger_type='Tesla'` `fast_charger_brand=''` `charger_power=55` `conn_charge_cable='SAE'` |
| 2026-08-18 07:12 | 自宅ウォールコネクターで48A充電中 | `fast_charger_present=False` `fast_charger_type='ACSingleWireCAN'` `fast_charger_brand='Tesla'` `charger_power=9` `conn_charge_cable='SAE'` |

`fast_charger_brand` は上記2件で値が逆転しており、`conn_charge_cable` は両方とも同じ値だった。いずれも判定には使えない。

2026-08-10 にテンフィールズファクトリーのFLASH（NACS）で充電した際は、これらの値を記録する仕組みが無く取り逃した。**非Teslaの急速充電器での値は未観測である。**

#### フル充電モードとの関係

**外出先の判定はフル充電モードより優先される。**オーバーライドの目的は「自宅で太陽光の発電状況を無視して充電する」ことであり、外出先では意味を持たない。ON のまま外出しても、外出先ではコマンドを送らない。

これにより、**従来の回避策（外出前にフル充電モードをONにする）は不要になった。**

#### ログの見え方

外出先と判断している間は、毎サイクル `ATTENTION` を出す。無言で見送ると「システムが動いていないのか、意図して見送っているのか」を区別できないため、抑制していない。

```text
[ATTENTION] 夜間休止中に充電を検知しましたが、急速充電器での充電を検知したため、外出先での充電と判断して停止しません。 [fast_charger_present=True fast_charger_type='Tesla' fast_charger_brand='' charger_power=55 conn_charge_cable='SAE']
[ATTENTION] 自宅のウォールコネクターに接続されていないため、外出先での充電と判断し、電流調整・停止・開始のいずれも行いません。 [fast_charger_present=False ...]
```

**どちらの根拠で外出先と判断したかが文面に現れる。**根拠1（急速充電の検知）で確定した場合、自宅のウォールコネクターは読んでいない。2台目や来客のEVが接続中の場面で「接続されていないため」と記録すると事実と反するため、根拠ごとに文面を変えている。

**行末の角括弧には、急速充電フィールドの実値を毎回書き出している。**これらの値は未検証であり（前述）、判定が働いた場面で記録しておかないと、フォールバックが正しく効くかを後から検証する手段が無い。2026-08-10、テンフィールズファクトリーのFLASHで充電した際、これらの値がログに残っておらず実機データを取り逃した。外出先での充電後は、この行を確認して値を蓄積すること。

夜間にこの判定が出ている間、**`NIGHT_STOP_MAX_ATTEMPTS`（6回）のカウンタは消費されない。**通信の失敗ではないためである。長時間の外出先充電のあとに帰宅しても、その夜の監視は生きており、自宅で始まった充電は通常どおり停止できる。

#### 設定

`tesla_config.json` に以下を設定する。`WALL_CONNECTOR_HOST` が空の場合、この判定は一切行われず、全経路が従来どおりの動作になる。

| キー | 既定値 | 内容 |
| --- | --- | --- |
| `WALL_CONNECTOR_HOST` | `""` | 自宅ウォールコネクターのIPアドレス。**ルーター側でDHCP予約を行い、アドレスを固定すること** |
| `WALL_CONNECTOR_TIMEOUT_SEC` | `5` | HTTPタイムアウト秒 |
| `WALL_CONNECTOR_ATTEMPTS` | `2` | 読み取り失敗時に、その場で取り直す回数（1回目を含む） |
| `WALL_CONNECTOR_SERIAL` | `""` | 任意。設定した場合のみ起動時に照合する |
| `FAST_CHARGER_POWER_KW` | `15` | フォールバックの閾値 |

起動時に個体を確認し、ログへ残す。設定を間違えたまま「判定が効いているつもり」になる状態を、サービス再起動のたびに顕在化させるためである。

```text
[INFO] 自宅ウォールコネクター（<ウォールコネクターのIP> / シリアル <シリアル番号>）を確認しました。
```

#### 対象となるウォールコネクター

**Gen 3（Wi-Fi対応）に限る。**Gen 2 や、Wi-Fiを宅内LANに接続していない個体では判定できない。エンドポイントはTeslaが公式に文書化したものではなく、いつ塞がれてもおかしくない。塞がれた場合は判定不能となり、自動的に従来動作へ縮退する。

#### ケーブル未接続の車は起こさない

**充電ケーブルが自宅の充電器に繋がっていないと分かっている間は、就寝中の車両を起こさない。**起こしても `Disconnected` を読み直すだけで、充電は始められないためである。

ケーブルを挿せば車両は自らオンラインになり、**課金されない車両リストで検知できる。**確認のためにウェイク（¥2.75/件）を送る必要はない。

```text
[INFO] 自宅の充電器にケーブルが接続されていないため、車両を起こしません。
```

判断は**毎サイクル、その時点のウォールコネクターの応答で行う。**決め打ちの時間で見送るのではないため、盲目区間は生じない。ケーブルを接続すれば次のサイクル（最大10分）で通常の判断に戻る。

| ウォールコネクターの応答 | 挙動 |
| --- | --- |
| 未接続 | 起こさない |
| 接続あり | 従来どおりの判断（余剰またはフル充電モード）へ |
| 読み取れない | **従来と完全に同じ挙動**（`TERMINAL_WAKE_SUPPRESS_SEC` の経過後に起こす） |

対象は `Disconnected` に限る。`Complete`（満充電）と `NoPower`（給電なし）は、車両側の動作なしに解消しうるため定期的な確認に意味があり、扱いを変えていない。

**起動直後の1回は起こす。**まだ充電状態を観測していないため、状態を知る手段が他にない。

##### この対策が必要になった事象

2026-08-12、フル充電モードが37時間42分ONのままで、ケーブル未接続の車を**約71分ごとに13回起動**していた（13回すべてがオーバーライド起因、約¥36）。

オーバーライド中は余剰チェックを迂回して起動するため、終端ステータスの抑止（1時間）が切れるたびに必ず起こしていた。起こした結果は毎回 `Disconnected` で、抑止を再設定して同じことを繰り返していた。

#### 既知の制約：複数の車両に対応していない

**このシステムは車両が1台であることを前提にしている。**次の2つの状況は現時点で未対応であり、
将来的に対応が必要である。

* **テスラ車を複数所有している場合**
* **自宅のウォールコネクターを複数の車両が使う場合**（2台目、来客のEVなど）

##### 何が起きるか

**制御対象は常に車両リストの先頭の1台だけである。** `GET /api/1/vehicles` の応答から
`vehicles[0]` を取り出しており、2台目以降は存在しないものとして扱われる。

さらに、**車両リストの順序に保証はない。** 順序が入れ替われば、システムは無言で制御対象を
別の車へ切り替える。1台のうちは起こらないが、複数所有では「今日はA号車、明日はB号車」に
なりうる。どちらを制御しているかを利用者へ知らせる手段も現在は無い。

**充電場所の判定も、複数車両では成立しない。** ウォールコネクターのローカルAPIは
`vehicle_connected` を返すが、これが意味するのは「**何らかの車が**自宅の充電器に繋がっている」
であって「**制御対象の車が**繋がっている」ではない。`/api/1/vitals` にVINは含まれない
（実機で全フィールドを確認済み）。

したがって次の組み合わせを判別できない。

```text
制御対象の車 = 外出先のAC充電器（デスティネーションチャージャー等）で充電中
自宅の充電器 = 別の車（2台目・来客EV）が接続中 → vehicle_connected: true
  ↓
車両側の charge_state は AC か DC かしか答えず、場所を答えない
ウォールコネクターは true を返すが、それが制御対象の車である保証がない
  ↓
外出先と判定できず、自宅にいるものとして制御してしまう
```

このとき、別の車が消費している電力は系統電力に現れるため、**余剰不足と判定されて
外出先の充電を停止させる**ことになる。

なお **DC急速充電の場合は判別できる。** 自宅の充電設備はACであり、DC急速充電を検知したなら
自宅ではありえないためである。この判定は車両ごとの `charge_state` に基づくため、
別の車が自宅の充電器を使っていても影響を受けない。

##### 来客のEVそのものには影響しない

来客のEVへコマンドが送られることはない。車両コマンドは利用者のTeslaアカウントにある
VIN宛にしか送れず、別アカウントの車には到達しない。ウォールコネクターへの通信も
`/api/1/vitals` と `/api/1/version` の読み取りのみで、書き込みは一切行わない。

**ただし夜間休止も適用されない。** 来客のEVが夜間に接続されていれば朝まで系統から充電を
続けるが、システムはこれを検知も停止もできない（Tesla APIから見えないため）。

##### 対応の方向

対応する場合、少なくとも次の2つが要る。

* **制御対象の車両を明示的に指定する。** 設定に `TESLA_VIN` を追加し、指定があれば
  その VIN の車両をリストから選ぶ。未指定なら従来どおり先頭を使い、車両が複数ある場合は
  起動時に警告する
* **ウォールコネクターに繋がっている車両を特定する。** 現時点で確実な手段は
  `GET /api/1/energy_sites/{id}/live_status` の `wall_connectors[].vin` のみである。
  `energy_device_data` スコープの追加と再認可が必要で、ウォールコネクターがTeslaの
  エネルギーサイトとして登録されていることが前提になる（本システムの構成で取得できるかは未確認）

VIN自体は、ウォールコネクターと車両のあいだのCP線を流れる single-wire CAN 上に存在する
（Synacktiv による解析で読み取り可能であることが示されている）。しかしローカルHTTP APIには
出ておらず、取得にはCP線へ機器を割り込ませる必要がある。**充電設備の制御線に常設の機器を
加えることになり、得られる利益に釣り合わないため採らない。**

#### 検討して採らなかった案

* `drive_state` の緯度経度を自宅座標と比較する。判別能力は同等だが、`vehicle_location` スコープの追加と再認可が必要になる
* `energy_sites/{id}/live_status` の `wall_connectors[]`（`din` と接続中の車両の `vin` が取れる）。`energy_device_data` スコープの追加が必要で、かつTeslaのエネルギーサイト（Powerwall等）への紐付けが前提となる公算が大きい
